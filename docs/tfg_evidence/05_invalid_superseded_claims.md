# 05 — Superseded and Invalid Claims

Purpose: prevent a future session (or the thesis text itself) from resurrecting a mistake that was already found and corrected during this project. Each entry states the old claim, why it's wrong/superseded, and what replaced it.

| # | Old claim | Why superseded/invalid | Replaced by | Evidence |
|---|---|---|---|---|
| 1 | NetIO (nwlab.net protocol) is the intended/final benchmark tool for this TFG | Was true only relative to the `clean-benchmark` branch's own visible history; a separate, never-merged branch (`origin/procotol`) showed the project had actually moved to RT-Thread's `netutils` `iperf` package | netutils iperf (`packages/netutils-latest/iperf/iperf.c`, commit `b77ba3f...`) | `02_experiment_history.md` Events 2-3 |
| 2 | The benchmark's TCP PCB exposes a field called `snd_una` | Never true for lwIP 2.0.3's `struct tcp_pcb` — the field simply does not exist under that name | `lastack` (`u32_t`, "Highest acknowledged seqno") | `tcp.h:257`; zero grep matches for `snd_una` |
| 3 | `tcp_poll()` can be used as a periodic active-transfer sampling clock (fires roughly every `pollinterval × TCP_SLOW_INTERVAL` regardless of connection activity) | Disproven empirically and from source: `tcp_in.c:1203` resets the poll countdown on every processed ACK. During a continuously-ACKed bulk transfer it essentially never fires (`sample_count=0` after 30s live) | `tcp_poll` is valid only as an idle-connection detector; a genuine periodic sampler needs an ACK-independent trigger (timer-based, or hooking a different callback) — **not yet designed**, see `02_experiment_history.md` Event 18 | `01_verified_facts.md` F27-F28; `02_experiment_history.md` Events 14-17 |
| 4 | One application `send()`/write() call corresponds to one TCP segment or one pbuf | Never asserted as true and directly contradicted by source: `IPERF_BUFSZ=4096` bytes per `send()` call is far larger than `TCP_MSS=1460`; lwIP internally re-chunks into MSS-sized segments via `tcp_write()`'s own segmentation logic. No 1:1 mapping exists at any layer inspected | Application write size (4096B) and network segment size (MSS=1460B) are two separate, independently-established facts — do not conflate them | `01_verified_facts.md` F01, F14 |
| 5 | 32768 is the absolute maximum possible `TCP_SND_BUF` for this build | Not licensed by the evidence. 32768 only fails **because `TCP_SND_QUEUELEN` is fixed at 22** in the frozen matrix. With `TCP_SND_QUEUELEN` raised to satisfy the constraint, values up to 65535 compile without error (and 65536 compiles too, just wrongly). The true, QUEUELEN-independent ceiling is the `u16_t` type width (65535), not 32768 | "32768 is the max **with `TCP_SND_QUEUELEN` fixed at the baseline value of 22**"; the type-level ceiling is 65535; 65536 is excluded separately (Event 9) | `01_verified_facts.md` F07, F32-F34; `03_phase0_results.md` A3-A4 |
| 6 | Any fixed repetition count or fixed discard/duration value from an earlier, informal test plan | No single fixed rep-count or duration was ever formally adopted before this session's frozen matrix. Ad hoc pilot runs used ~30s and single (non-repeated) trials | Formal protocol: **5 repetitions per cell**, **~30 s target duration per run**, documented in `experiment/manifest.yaml` | `00_project_state.md`; `experiment/manifest.yaml` |
| 7 | Any earlier A/B/C/D/E/F-labeled experimental matrix broader than the current B/C/D scheme | The currently frozen matrix has exactly three independent-variable experiments (B=`TCP_SND_BUF`, C=`TCP_SND_QUEUELEN`, D=`MEMP_NUM_TCP_SEG`) plus a shared baseline, not six letters' worth. No evidence in currently-visible context of a formally adopted "E" or "F" experiment | 6 unique configs: BASE, B1, C1, C2, D1, D2 (see `00_project_state.md`) | `experiment/manifest.yaml` |
| 8 | Attribution/interpretation of results based only on a bare `B/RTT` ratio (bandwidth divided by RTT, with no reference to window/buffer state) | Superseded by the discovery that BDP-based reasoning requires knowing `TCP_WND`/`cwnd`/in-flight bytes, none of which were ever actually sampled during any transfer to date (`sample_count=0` in every attempted instrumented run) | Any BDP/window-based interpretation must wait for working sender-state samples from a redesigned sampler | `02_experiment_history.md` Events 15-18 |
| 9 | `MEM_SIZE` is a meaningful constraint on `TCP_SND_BUF` / a resource that TCP send buffering consumes | Investigated and disproven in an earlier part of this session: `mem_malloc`/`mem_free` in this port are overridden in `port/sys_arch.c` to call `rt_malloc`/`rt_free` directly; lwIP's own `mem.c` (the only file that references `MEM_SIZE`) is excluded from the compiled source list. `MEM_SIZE` is dead configuration — never read by any linked object file. (A planned A/B runtime test to double-check this was itself abandoned mid-task, once the source evidence made the test pointless — see below.) | Two facts, not to be conflated: **PBUF_RAM** (TCP payload data, e.g. the bytes in `unsent`/`unacked` segments) is backed by the RT-Thread `rt_malloc` heap (~64MB region); **`MEMP_NUM_TCP_SEG`** (segment *metadata* — the `struct tcp_seg` records) is backed by a separate **static memp/BSS pool** sized at compile time. Neither is backed by `MEM_SIZE`. | `01_verified_facts.md`; the abandoned A/B test is itself a recorded methodology finding — a planned MEM_SIZE=1600-vs-16384 runtime comparison was correctly cancelled before running, once source inspection showed both configurations would be behaviourally identical (the macro is dead), avoiding a wasted/meaningless test |
| 10 | Ubuntu→RT-Thread is a valid direction for the Phase 1 sender-resource dataset | Both directions were shown to work mechanically, but only RT-Thread→Ubuntu isolates the sender-side resources under test, given the confirmed netem-egress-only delay mechanism | RT-Thread→Ubuntu only, formally adopted | `02_experiment_history.md` Event 4 |
